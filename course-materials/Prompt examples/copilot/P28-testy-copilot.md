Pracuję z GitHub Copilot nad wybraną aplikacją z zatwierdzonego startera albo osobnego repozytorium legacy. Przeczytaj aktualny PRD, odpowiednie ADR-y, instrukcje repozytorium i istniejące testy. Nie przeszukuj course-materials poza plikiem, który wskażę. Jeśli aplikacja nie istnieje, zatrzymaj się na planie testów i wskaż potrzebny starter; nie udawaj uruchomionych testów.

Wybierz ze mną jedno kryterium akceptacji: na przykład zgłoszenie reklamacji z nieprawidłową datą zakupu. Przygotuj mały plan testów: przypadek poprawny, graniczny, błąd, oczekiwany komunikat i dane syntetyczne. Dla UI użyj istniejącego runnera E2E, np. Playwright. Dla Pythona użyj pytest, jeśli projekt go stosuje; dla innego języka zachowaj jego rzeczywisty runner. Najpierw sprawdź konfigurację i dokładne polecenie projektu, nie instaluj drugiego runnera obok istniejącego bez uzgodnienia.

Dodaj jeden test zachowania i uruchom go. Jeśli ujawnia brak funkcji, pokaż ten błąd, a nie brak importu czy zależności. Nie zmieniaj kodu aplikacji w tym kroku. Jeśli test od razu przechodzi dla uzgodnionego kryterium, zgłoś istniejące pokrycie; nie zmieniaj produkcji, asercji ani danych, aby wymusić fazę Red. Dla charakterystyki działającego kodu najpierw zachowaj zielony punkt odniesienia. Tylko dla potwierdzonego braku funkcji, po moim zatwierdzeniu wykonaj najmniejszą implementację i uruchom test oraz właściwą regresję. W E2E użyj uruchomionej aplikacji, deterministycznych danych i stabilnych lokatorów użytkownika. Nie obchodź uprawnień ani nie używaj produkcyjnych kont.

Na końcu zwróć: mapę AC -> test -> plik, polecenie i rzeczywisty wynik, istotny diff asercji oraz to, czego nie sprawdzono. W niezależnym przeglądzie oceń, czy test wykryje kontrolowaną zmianę zachowania. Nie osłabiaj asercji, nie usuwaj testów i nie zastępuj błędu retry.
